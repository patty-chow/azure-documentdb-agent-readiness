# Add a bulk and idempotent data ingestion how-to for Azure DocumentDB

**Proposed location:** a new how-to in the Azure DocumentDB developer guide (for example `how-to-bulk-ingest-data`), next to [Indexing best practices](https://learn.microsoft.com/en-us/azure/documentdb/how-to-create-indexes). Link it from the "Insert documents" steps of the Python and Node.js quickstarts, from the indexing pages, and from "Batch limits" on [Service limits](https://learn.microsoft.com/en-us/azure/documentdb/limitations).

## What happens today

Each piece of a safe ingestion pattern is documented on its own page. No page connects them into a recipe for a seed or load script that can run twice:

- The [`$setOnInsert` reference](https://learn.microsoft.com/en-us/documentdb/query/operators/field-update/$setoninsert) shows a single-document upsert. It has no batch example and no guidance on idempotency keys.
- The [MQL compatibility page](https://learn.microsoft.com/en-us/azure/documentdb/compatibility-query-language) lists the server `bulkWrite` command as not supported, and says functions built on supported commands (`insert`, `update`, `delete`) work. It does not explain what this means for driver bulk APIs.
- [Service limits](https://learn.microsoft.com/en-us/azure/documentdb/limitations) gives the 25,000-writes-per-batch limit, the 2 KB `_id` limit, and says unique index builds run in the foreground and block writes. These are listed as limits, with no ingestion guidance.
- [Indexing best practices](https://learn.microsoft.com/en-us/azure/documentdb/how-to-create-indexes) says to build indexes after a large load, and to use `blocking: true` on an empty collection. It does not cover unique indexes used as idempotency guards.
- The quickstarts show a single `insert_many` / `insertMany`. The [Agent Kit](https://github.com/Azure/documentdb-agent-kit) covers TTL (`skills/indexing/index-ttl-expiry.md`) but has no upsert, bulk-write or idempotency-key guidance; `skills/local-deployment/local-sample-data-management.md:72` says "Idempotent scripts only", yet the example in that section (line 63) is a plain `insertMany`. The DocumentDB table of contents has no entry for bulk, ingest, retry or throttling. Probed URLs such as `/azure/documentdb/how-to-bulk-write` return 404.

Agents without a page to follow fell back to prior knowledge or to RU-based Azure Cosmos DB for MongoDB pages (`troubleshoot-request-rate-too-large`, `optimize-write-performance`). Those pages don't apply to Azure DocumentDB, which is sized by vCore (M-series) tiers and has no request units.

## Why it matters

We had an AI agent (gpt-5-mini, with the Azure DocumentDB Agent Kit and the DocumentDB, Azure and Learn MCP servers) build 100 sample apps. Every prompt asked for a seed script that loads data, creates the index, and can run twice without duplicating data. **17 of the 100 samples** hit this gap (26 findings). The counts come from one experiment run and may shift on a re-run. What the agent did wrong:

- Called `insert_many` behind a unique index, so a second run raised `DuplicateKeyError`, which was caught and printed instead of upserted.
- Claimed in the README that the seed was idempotent while inserting duplicates in a loop on every run.
- Upserted with `$set` on every field, so `createdAt` was overwritten on each refresh.
- Looped single-document upserts with no batching or backoff; called `bulk_write` from prior knowledge with no `BulkWriteError` handling.
- Invented ad hoc canonical keys (parameter hashes, sorted pair keys, composite option-chain keys) and did not canonicalize identifiers at ingest.
- Left index creation implicit in ODM startup; stored sessions without a TTL index; skipped a target-database check and a clean-up section.
- Imported RU-based throttling ideas (request units, 429 handling) from Azure Cosmos DB for MongoDB pages. Azure DocumentDB has no request units and never returns error 16500 or HTTP 429: neither code exists in the engine's error mappings, the Learn troubleshooting table lists no throttling code, and no run received one. Its resource-pressure signals are timeouts and latency (code 50 `ExceededTimeLimit` after the 120-second default query limit) and, when the backend connection limit is exhausted, code 261 `TooManyLogicalSessions`.

Seed scripts are the first code a developer runs against a new cluster and the most-copied code in any sample, so this gap spreads.

## Proposed change

One page, about two screens, with PyMongo and Node.js snippets:

1. **Which bulk APIs work.** Collection-level `Collection.bulk_write` (PyMongo), `collection.bulkWrite` (Node) and Mongoose `Model.bulkWrite` send `insert`/`update`/`delete` and are supported; a run in this experiment executed `coll.bulkWrite(ops, {ordered: false})` against the service and got `ok: 1, nUpserted: 200`. Client-level `MongoClient.bulk_write` / `client.bulkWrite` send the MongoDB 8.0 database-level `bulkWrite` command (multi-namespace; Node driver 6.10 or later), which the compatibility page marks as not supported and the engine rejects (the engine stub raises `CommandNotSupported` "bulkWrite is not yet implemented"; the release/1.0-RC2 gateway returns 59 `CommandNotFound`). Say this explicitly, because the compatibility page's `bulkWrite | No` row does not distinguish the two. Use `ordered=False` for loads. Also ask the [MQL compatibility page](https://learn.microsoft.com/en-us/azure/documentdb/compatibility-query-language) to footnote the `bulkWrite` row as the 8.0 database command and to state that collection-level `bulkWrite()` works.
2. **Batch size and limits.** State the 25,000-writes-per-batch hard limit ("Batch operations exceeding 25,000 writes will fail. No limit on the total number of batch operations.") and link "Batch limits". Tell readers to chunk at or below 25,000 operations per request regardless of what the driver's `hello.maxWriteBatchSize` says, since the gateway's compiled default advertises 100,000 while the engine refuses more than 25,000. No per-tier figure is published for Azure DocumentDB (the 1,000-documents-per-`insertMany` figure lives on the RU-based Azure Cosmos DB for MongoDB page, a different service), so until the docs team supplies one, present 1,000 operations per `bulk_write` call with `ordered=False` and a handful of parallel workers as a starting point, not a Learn figure, and cite the trial-and-extrapolate method on [Migration options](https://learn.microsoft.com/en-us/azure/documentdb/migration-options) ("Run a trial migration on a small but representative dataset", "Scale up during migration, then scale down after cutover"). Recommended starting sizes per M-series tier remain open question 1. [needs SME confirmation] Also ask "Batch limits" on Service limits to name the error a client sees when a request exceeds 25,000 writes and to state whether `hello.maxWriteBatchSize` reflects 25,000 (on documentdb-local 0.117 the gateway advertised 25,000, so `insert_many` of 25,001 documents was split by the driver, and a raw command with 25,001 operations failed with code 16 `InvalidLength` "Write batch size must fall within the range of 1 to 25000"; see findings/phase4/ENGINE-TESTS.md, not yet verified on the managed service).
3. **Pick an idempotency key.** Compare a deterministic `_id` (simplest filter, uses the built-in index; keep it under 2 KB, hash long keys) with a natural key backed by a unique compound index such as `createIndex({tenantId:1, orderNumber:1}, {unique:true})`. Without that unique index, concurrent filter-based upserts can insert duplicates. Show three key shapes: a composite business key, a sorted pair key (`<minId>_<maxId>`), and a hash of canonicalized parameters (keys sorted before hashing). Show canonicalizing identifiers before writing (normalized email, digits-only phone).
4. **Upsert correctly.** `update_one(filter, {'$set': {...}, '$setOnInsert': {'createdAt': now}}, upsert=True)`; `$inc` for counters; `ReplaceOne(..., upsert=True)` to refresh whole documents; aggregation-then-upsert (or `$merge`) for derived collections.
5. **Handle errors.** Inspect `BulkWriteError.details['writeErrors']`; treat duplicate key 11000 as success for idempotent writes; retry only failed operations; verify with upserted and matched counts. Show the Node equivalent with `collection.bulkWrite(ops, {ordered: false})` and `MongoBulkWriteError`. Example:
   ```python
   ops = [UpdateOne({'_id': d['_id']}, {'$set': d, '$setOnInsert': {'createdAt': now}}, upsert=True) for d in docs]
   for i in range(0, len(ops), BATCH):
       try:
           coll.bulk_write(ops[i:i+BATCH], ordered=False)  # collection-level
       except BulkWriteError as e:
           if [w for w in e.details['writeErrors'] if w['code'] != 11000]: raise
   ```
6. **Retries and capacity.** Explain why `retrywrites=false` is required, with the de-duplication reason, since no Learn page states it today. Suggested text: "Keep `retrywrites=false` in every Azure DocumentDB connection string. The service does not support retryable writes: the server does not de-duplicate a retried write, so a driver retry can apply a non-idempotent write twice. Handle transient write failures in application code with idempotent operations (upserts, deterministic keys)." Then show application-level retry with exponential backoff and jitter for transient errors, safe only because the writes are idempotent. Name what to retry on: network and connection errors, code 50 `ExceededTimeLimit` (the default 120-second query limit, overridable with `maxTimeMS`; also "Exceeded time limit while waiting for a new primary to be elected" during a failover), 6 `HostUnreachable` and 91 `ShutdownInProgress`. Name what not to code against: 16500 and HTTP 429 (never returned by Azure DocumentDB; they are request-unit codes of the RU-based Azure Cosmos DB for MongoDB), 189 `PrimarySteppedDown` (not in the engine), 261 `TooManyLogicalSessions` ("There are too many open connections.": reduce the pool, don't retry) and 20 `IllegalOperation` ("Cannot execute the operation on this replica cluster": the script is pointed at a replica or demoted cluster). The server does not add `RetryableWriteError` or `TransientTransactionError` labels, so drivers never retry writes on their own; the [reliability page](https://learn.microsoft.com/en-us/azure/reliability/reliability-documentdb) puts retry on the application: "In-flight requests that weren't acknowledged before failover can fail and must be retried by the client" and "design write operations to be idempotent so that retrying them is safe." For large loads, watch CPU, memory and IOPS for the tier and scale the tier or storage if needed, rather than looking for request-unit throttling.
7. **Index order.** Build the unique index that enforces idempotency first, on the empty collection with `blocking: true`; it fails if duplicates exist. `blocking` is a DocumentDB-specific `createIndexes` option (MongoDB has none), default `false`, documented on [Indexing best practices](https://learn.microsoft.com/en-us/azure/documentdb/how-to-create-indexes) with no server-version qualifier ("Setting { \"blocking\": true } is useful in migration utilities where indexes are created on empty collections before data writes commence"); the page should label it as DocumentDB-specific. Current Learn says unique-index builds run in the foreground and block writes (Service limits) or "block read and write operations" (compatibility page); the engine default `enableNonBlockingUniqueIndexBuild=true` suggests this may be stale, so keep the conservative wording "expect a unique index build to block writes; create it before loading data" until open question 2 is answered. Build other secondary indexes after a large initial load. For cosmosSearch vector indexes, follow the documented build order: an HNSW index can be created on an empty collection; an IVF index (`numLists` = documentCount/1000 up to one million documents, so it depends on the final document count) and a DiskANN index with product quantization should be created after the load; a new vector index can return empty results for 2 to 3 minutes while it builds, so the script should not treat an empty first query as a failure. Only one vector index can exist per vector path, so the script's ensure-index step should look the index up by name in `listIndexes` (Learn's vector-search page shows the options under `cosmosSearch`; documentdb-local 0.117 reports them under `cosmosSearchOptions`, so match on the index name and read either key) and tolerate either outcome of re-issuing the same `createIndexes` call (a no-op or an error; on documentdb-local 0.117 an identical call is a no-op and a second index on the same path fails with code 85 `IndexOptionsConflict`, per findings/phase4/ENGINE-TESTS.md), rather than asserting a particular error code. In production, create indexes in a migration step, not implicitly at app startup.
8. **TTL for ephemeral data.** `createIndex({createdAt:1}, {expireAfterSeconds: 3600})`; the index must be single-field and the field a BSON Date. Link the TTL entry in the compatibility table.
9. **Embeddings during ingest.** Rate-limit and cache embedding-provider calls. Store vectors as an array of numbers (`number[]` / `list[float]`), never as BSON binary: a document whose vector field is BSON binary is stored and returned intact but is not indexed by a cosmosSearch index and is silently absent from vector-search results, and a BSON binary query vector is rejected ("expected an array type field"). The page should name BSON binary explicitly, since the current Learn wording only says the field must be an array of numbers. Keep dimensions within the documented limits: 2,000 without compression, 4,000 with `compression: "half"` on HNSW or IVF, 16,000 with product quantization on DiskANN.
10. **Script template and clean-up.** Read the connection string from an environment variable, never hard-coded; check that the database name matches the expected sample database; require `--confirm` / `--force`; create indexes, bulk upsert, print counts. End with a Clean up section: drop the collection, drop the cosmosSearch vector index by name, and a reminder to run `az documentdb mongocluster delete`.

Also ask the owners of the RU-based Cosmos DB for MongoDB throttling pages to add a note that they don't apply to Azure DocumentDB, and ask [Troubleshoot common issues](https://learn.microsoft.com/en-us/azure/documentdb/troubleshoot-common-issues) to say explicitly that Azure DocumentDB has no request-unit throttling and never returns 16500/429, and to add the codes a bulk-write client meets that its Error Codes table omits (6, 50, 91, 261; 59 for the 8.0 `bulkWrite` command).

**Follow-up (separate PR, Azure/documentdb-agent-kit, after the page exists):** link the page from `skills/data-modeling/SKILL.md`, and in `skills/local-deployment/local-sample-data-management.md` replace the non-idempotent `insertMany` example with an upsert-based collection-level `bulkWrite`. Coordinate with the kit seeding/bulk-load PR (drafts 053, 086, 103) so the two don't overlap, and with the fix to `skills/connection/SKILL.md:230`, whose retry helper retries only on `err.code === 16500 || err.code === 429` and therefore never retries a real transient error.

## Resolved

- retryWrites: answered 2026-11-25, see findings/phase4/DECISIONS.md. Retryable writes are not supported; retrywrites=false is required; the server does not de-duplicate retried writes (documentdb/documentdb#767).
- Vector-index facts: settled 2026-11-25 from the Learn vector-search, half-precision, product-quantization and limitations pages and engine issue documentdb/documentdb#109, see findings/phase4/DECISIONS.md.
  - Build order for vector indexes in a seed script: HNSW can be created on an empty collection; IVF `numLists` depends on document count and a product-quantization index should be created after the collection has data; a new index can return empty results for 2 to 3 minutes while it builds (vector-search page, HNSW and IVF tabs; product-quantization page note; quickstart-nodejs-select-algorithm Troubleshooting).
  - Vectors stored as BSON binary are stored and returned but not indexed and are absent from results; a binary query vector is rejected with "expected an array type field" (vector-search page, DiskANN field table and IVF Important box; documentdb/documentdb#109).
  - Dimension limits to quote: 2,000 uncompressed, 4,000 half-precision on HNSW and IVF, 16,000 product quantization on DiskANN (vector-search "Features and limitations"; half-precision, product-quantization and limitations pages).
  - One index per vector path; `listIndexes` reports options under `cosmosSearch` (vector-search features list and "Get vector index definitions"; limitations page).
- Error 16500 / HTTP 429 under load: settled 2026-11-25, no. Azure DocumentDB never returns 16500, 429 or any throttling code; 16500 is a request-unit error of the RU-based Azure Cosmos DB for MongoDB, the engine at commit a5f1636 has no such code and no rate-limiting path, the Learn troubleshooting table lists none, and no run received one; resource pressure shows as timeouts (code 50 `ExceededTimeLimit`, 120-second default) and 261 `TooManyLogicalSessions` when the connection limit is hit. Sources: https://learn.microsoft.com/en-us/azure/cosmos-db/mongodb/error-codes-solutions (row 16500, RU-based API); https://learn.microsoft.com/en-us/azure/documentdb/troubleshoot-common-issues (Error Codes table); https://learn.microsoft.com/en-us/azure/documentdb/limitations (MongoDB execution limitations); github.com/documentdb/documentdb @ a5f1636 error_mappings.csv, documentdb_errors.csv, pg_documentdb_gw/include/all_error_mappings_oss_generated.csv, responses/pg.rs:277-295 and :507-511; runs/*/events.jsonl (120 runs, no throttling code); see findings/phase4/DECISIONS.md, throttling topic.
- Client-level vs collection-level bulk writes: settled 2026-11-25. The compatibility page's `bulkWrite | No` row is the MongoDB 8.0 database-level command that `MongoClient.bulk_write` / `client.bulkWrite` send (Node driver 6.10+, server 8.0), which the engine stub rejects with `CommandNotSupported` "bulkWrite is not yet implemented" (59 `CommandNotFound` from the RC2 gateway); collection-level `bulkWrite()` maps to `insert`/`update`/`delete` and works, observed as `ok: 1, nUpserted: 200` in run 02-real-time-event-stream-ingestion/20261124-203233. Sources: https://learn.microsoft.com/en-us/azure/documentdb/compatibility-query-language (Database commands table and note); https://www.mongodb.com/docs/manual/reference/command/bulkWrite/; https://www.mongodb.com/docs/drivers/node/current/crud/bulk-write/; https://github.com/documentdb/documentdb/blob/main/pg_documentdb/src/commands/bulk_write.c; documentdb/documentdb#770 and #108; runs/02-real-time-event-stream-ingestion/20261124-203233/events.jsonl; see findings/phase4/DECISIONS.md, transactions and bulk topic.
- `blocking: true` currency: settled 2026-11-25. It is a DocumentDB-specific `createIndexes` option, default `false`, parsed as a boolean-like top-level field and building non-concurrently when true, documented on Learn with no server-version qualifier; the wire-protocol version (5.0-8.0) does not gate it. Sources: https://learn.microsoft.com/en-us/azure/documentdb/how-to-create-indexes ("Prioritizing Index Builds over new Write Operations using the Blocking Option"); https://learn.microsoft.com/en-us/azure/documentdb/partitioning (How to shard a collection); https://github.com/documentdb/documentdb/blob/main/pg_documentdb/src/commands/create_indexes.c lines 1074-1077, 1827, 1875-1882; see findings/phase4/DECISIONS.md, transactions and bulk topic. The unique-index foreground/blocking question stays open (open question 2).
