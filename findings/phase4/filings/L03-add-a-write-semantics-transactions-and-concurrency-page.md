# Add a write semantics, transactions and concurrency page for Azure DocumentDB (retrywrites, write concern, idempotency)

## What happens today

Learn covers pieces of this on separate pages, which disagree on retryable writes:

- **Connection string.** Every quickstart (for example `quickstart-nodejs`) and the Entra ID page show `retrywrites=false&maxIdleTimeMS=120000` with no explanation. `tutorial-nodejs-mongoose` has a "Why keep retryWrites=false?" section that presents it as a sample choice rather than a service requirement, which is wrong: Azure DocumentDB does not support retryable writes, and `retrywrites=false` is required. `azure/reliability/reliability-documentdb` ("Resilience to transient faults") advises exponential backoff and idempotent writes, but also says to "use MongoDB drivers that support automatic retry handling". No Learn page (`limitations`, `compatibility-query-language`, the connect pages) states that retryable writes are unsupported or explains why: the server does not de-duplicate a retried write (documentdb/documentdb#767), so a driver retry can apply a non-idempotent write twice.
- **Transactions.** `how-to-transactions` shows the Node.js `withTransaction()` pattern; Python and Java get only manual start/commit. `limitations` states a 30-second lifetime, which `how-to-transactions` never mentions. `partitioning` documents that transactions span logical and physical shards, which `how-to-transactions` never mentions either. Nothing says which commands are refused inside a transaction (the troubleshooting table lists code 263 `OperationNotSupportedInTransaction` with no command list) or when to avoid a transaction. `how-to-transactions` says "The callback can run more than once if the driver retries the transaction", which presumes the `TransientTransactionError` label; the service returns code 112 `WriteConflict` (and 251 `NoSuchTransaction`) with an empty label list (documentdb/documentdb#339, reproduced against the managed service), so `withTransaction()` never retries a write conflict and the application must re-run the transaction itself.
- **Write and read concern.** `high-availability` and the reliability page document synchronous in-region HA and asynchronous cross-region replicas. No page says which client `w`/`j`/`wtimeoutMS`, `readConcern` or `readPreference` values are honored, ignored or rejected. In fact the DocumentDB gateway validates these options and discards them (durability comes from the cluster's HA configuration, not from `w`), rejects `readPreference: secondary`, tag sets and hedged reads outright, and answers `getDefaultRWConcern` with a constant majority/majority document that does not describe applied behaviour. `compatibility-query-language` lists only `getDefaultRWConcern` (supported) and `setDefaultRWConcern` (not supported).
- **Concurrency and bulk writes.** No page has an application retry sample, an optimistic-concurrency or job-lease recipe, or change-stream deduplication guidance. The compatibility page marks the `bulkWrite` command "No" without saying that the row is the MongoDB 8.0 database-level command and that collection-level `db.collection.bulkWrite()` (insert/update/delete) works, while `limitations` allows 25,000 writes per batch. `troubleshoot-common-issues` lists no throttling code and omits the codes a retry predicate needs (6, 20, 50, 91, 112, 251, 261).

## Why it matters

We ran 100 Azure DocumentDB sample prompts through a coding agent (gpt-5-mini) with the DocumentDB Agent Kit and the DocumentDB, Azure and Learn MCP servers. 64 audit findings from 42 of the 100 samples trace to this gap. Counts are from one experiment run. With no page to cite, the agent:

- set `retryWrites=true` in at least 19 generated apps, unlike the documented connection string; because the server does not de-duplicate retried writes, those apps can apply a retried non-idempotent write twice;
- shipped no application-level retry in most samples;
- left write and read concern at driver defaults in ledger samples, and twice recorded "client writeConcern is ignored" as fact from a Cosmos DB (RU) page rather than from any Azure DocumentDB source (the statement happens to hold here too, for a different reason: the gateway validates and discards `writeConcern`);
- imported 429/`RequestRateTooLarge` throttling advice from the RU-based Cosmos DB for MongoDB pages, codes that Azure DocumentDB never returns;
- versioned records by reading the max and inserting max+1, and used unconditional `updateOne` calls, so concurrent writers overwrite each other;
- wrote `startSession()`/`withTransaction()` code from prior knowledge, because no page shows the session pattern together with application-level retry of code 112 `WriteConflict`, which the service returns without the error label drivers retry on;
- computed aggregates such as drawdown client-side because it could not tell whether `$setWindowFields` is available on its server version;
- kept unbounded `$push` arrays, did not persist change-stream resume tokens, and guessed bulk batch sizes.

## Proposed change

Add a page, suggested slug `azure/documentdb/write-semantics-transactions-concurrency`, that builds on the "Resilience to transient faults" section of `reliability-documentdb` and links to it rather than restating it. Link the new page from the quickstarts (`quickstart-nodejs`, `quickstart-python`, `quickstart-dotnet`), `how-to-connect-mongo-shell`, `tutorial-nodejs-mongoose`, `change-streams`, `how-to-transactions`, `compatibility-query-language`, `limitations`, `high-availability` and `reliability-documentdb`. Sections:

1. **Retryable writes.** State that Azure DocumentDB does not support retryable writes and that `retrywrites=false` is required, and explain why, with the de-duplication reason: the server does not de-duplicate a retried write (documentdb/documentdb#767), so a driver with `retryWrites=true` gets no exactly-once protection and a retried non-idempotent write (for example `$inc`) can be applied twice, while a retried insert can report a duplicate key for a write that succeeded. Suggested wording: "Keep `retrywrites=false` in every Azure DocumentDB connection string. The service does not support retryable writes: the server does not de-duplicate a retried write, so a driver retry can apply a non-idempotent write twice. Handle transient write failures in application code with idempotent operations (upserts, deterministic keys)." Do not claim that `retryWrites=true` causes connection errors; that is not established. Say what the driver does on a transient failure: with `retrywrites=false`, and because the server never adds the `RetryableWriteError` label that drivers on 4.4+ wire versions retry on, the driver surfaces the error and the application owns the retry (make writes idempotent and wrap them in a bounded retry). Put the note directly under the connection string, mirror it in the quickstarts and the Entra ID page, add it to `limitations`, and replace the Mongoose tutorial's "sample choice" framing with it. Reword the reliability page's "use MongoDB drivers that support automatic retry handling" line so it no longer appears to contradict `retrywrites=false` (for example: drivers may retry server selection and reconnects, but write retries belong in application code).
2. **Application retry recipes.** PyMongo (for example a tenacity decorator) and Node.js/Mongoose `withRetry()` helpers used at the repository layer: initial delay 100-250 ms, factor 2, full jitter, at most 4-5 attempts. What to retry: network and connection errors, code 50 `ExceededTimeLimit` (the gateway's timeout code, "Consider increasing the maxTimeMS on the command"), 6 `HostUnreachable` and 91 `ShutdownInProgress` after a failover, and, inside a transaction, 112 `WriteConflict` and 251 `NoSuchTransaction` by re-running the whole transaction (the service sends no `TransientTransactionError` or `UnknownTransactionCommitResult` label, so `withTransaction()` will not do it). What never to retry blindly: duplicate key `11000`, validation and auth errors. What not to retry at all: 20 `IllegalOperation` ("Cannot execute the operation on this replica cluster", a write sent to a replica or demoted cluster: fix the connection string, prefer the global read-write string when a replica exists) and 261 `TooManyLogicalSessions` ("There are too many open connections": reduce pool size, do not back off and retry). State plainly that Azure DocumentDB has no request-unit throttling and never returns 16500/`TooManyRequests` or HTTP 429 (those are Cosmos DB RU codes, absent from the engine's error tables and from the troubleshooting page); resource pressure shows up as latency and timeouts (120-second default query limit, `maxTimeMS`), so `429`/`Retry-After` handling belongs to the embedding and LLM endpoints that RAG samples call, not to the cluster. During in-region HA failover, Learn documents "write slowness" and in-flight requests that "can fail and must be retried by the client" without naming a code; tell readers to treat connection errors and code 50 as transient and not to code against 10107/189, which the engine never emits for failover. Pair retries with idempotency keys or unique indexes; for unordered `bulkWrite`, retry only the transient `writeErrors`.
3. **Write concern, read concern, read preference.** State what the service does with each option, since Learn is silent today: the gateway validates `writeConcern` and the engine ignores it. `w: 0`, `w: 1` and `w: "majority"` are accepted; numeric `w` of 2 or more is rejected with `BadValue` ("w value exceeds the number of data-bearing voting members"); `j` and `wtimeout`/`wtimeoutMS` are accepted and ignored. `readConcern` `local` and `majority` are accepted; `available` and `linearizable` are rejected with `CommandNotSupported`; `snapshot` depends on gateway configuration (see open questions); a `readConcern` sent after a transaction has started is rejected with `InvalidOptions`. `readPreference` never routes a read anywhere: `primary`, `primaryPreferred`, `secondaryPreferred` and `nearest` are accepted and discarded (reads always go to the primary shards; standby shards serve no client traffic), while `secondary` and any tag set fail with `FailedToSatisfyReadPreference` and hedged reads with `BadValue`, so a client configured with `readPreference=secondary` fails rather than silently reading from the primary. Reads from a cross-region replica use that replica cluster's own connection string. Durability is a cluster property, not a client option: with in-region HA, writes are acknowledged only after being committed to primary and standby shards; without HA, each shard uses LRS storage with three synchronous copies. Replace the idea of a per-workload `w`/`readConcern` decision table with one recommendation: leave these options at their defaults (which is what the Learn how-to code does), and point read-heavy clients at the replica cluster's connection string. Show `db.adminCommand({ getDefaultRWConcern: 1 })` with a note that it returns a constant `{ defaultReadConcern: { level: "majority" }, defaultWriteConcern: { w: "majority", wtimeout: 0 }, ...Source: "implicit" }` document that describes what drivers may send, not what the engine applies, and that `setDefaultRWConcern` is not supported. Caveat for the page: this behaviour is read from the open-source DocumentDB gateway, which the Azure service is assumed to match (issue #339 was reproduced against the service); phrase it as "the DocumentDB gateway validates and discards these options".
4. **Transactions.** Scope: multi-document ACID transactions span multiple logical shards and multiple physical shards (`partitioning`, "Logical shards"; the Atlas comparison page says "Across collections and shards"); no Learn page states a cost difference for cross-shard transactions, so present it as reasoning, not fact. Limits: the 30-second lifetime (`limitations`; the gateway's compiled default, documentdb/documentdb#756), with no documented cap on operations, documents or bytes per transaction, so say "keep transactions short and small" and cross-link the 30-second limit from `how-to-transactions`. Commands refused inside a transaction return code 263 `OperationNotSupportedInTransaction`: describe them as categories rather than an exact list, since the gateway's main branch and its release branch differ (DDL and admin commands such as `createIndexes`, `createSearchIndexes`, `dropIndexes`, `drop`, `renameCollection`, `listCollections`, `currentOp` and `killOp`; data operations on the `admin`, `config` and `local` databases and on `system.*` collections; `killCursors` as the first statement). State that `WriteConflict` (112) and `NoSuchTransaction` (251) arrive without the `TransientTransactionError` label, so the driver's `withTransaction()` retry loop (120-second default) never triggers from a server error and a conflict surfaces to the application; a dropped connection during commit may still be retried by the driver's own `UnknownTransactionCommitResult` labelling, which was not verified against the service. Show the Node.js `withTransaction()` example wrapped in an application-level loop that catches code 112 and 251, re-runs the whole transaction with bounded attempts and backoff, and gives up after the 30-second lifetime; note that every operation in the callback must receive `{ session }`; add the Mongoose equivalent. State when to prefer a single-document atomic update (`findOneAndUpdate` with `$inc`/`$set`, or an upsert), for example on high-throughput ingestion or read-heavy vector-search paths. Add Python `with_transaction()` and Java `withTransaction()` snippets to `how-to-transactions`, and replace its sentence "The callback can run more than once if the driver retries the transaction".
5. **Optimistic concurrency and atomic patterns.** Version field: `updateOne({ _id, version: n }, { $set: {...}, $inc: { version: 1 } })`, treating `matchedCount === 0` (or a null `findOneAndUpdate` result) as a conflict, then re-reading and retrying a bounded number of times. Job lease: `findOneAndUpdate({ _id, status: 'submitted' }, { $set: { status: 'processing', owner, locked_at } })`, plus how to reclaim expired leases. Counter document with `$inc` and `upsert`. Bounded history with `$push` and `$slice`, citing the 16 MB limit. State that no server-side `_etag` or concurrency token is documented on Learn or present in the engine: optimistic concurrency is the application pattern above, as on MongoDB (engineering confirmation requested below).
6. **Change-stream consumers and bulk loads.** Make consumers idempotent: persist the resume token (and the last processed operation time) to a checkpoint collection after each batch and resume with `resumeAfter` or `startAtOperationTime`; deduplicate by event id (a unique index on an idempotency key with an upsert-based handler) instead of applying a blind `$inc`. State the documented resume model: resumption within the active 400 MB change log is cheap; beyond it, historical change streams transparently read archived logs back to 35 days or the cluster's creation (PITR integration), at higher resource cost, so run replays in low-traffic periods; multishard change streams and `updateDescription` are preview, `updateDescription` must be enabled per collection with `collMod`, multishard change streams cannot be enabled while the multishard rebalancer is on, and a single-shard to multishard transition breaks resumability; link `change-streams`. Footnote the compatibility page's `bulkWrite: No` row as the MongoDB 8.0 database-level command (`MongoClient.bulkWrite`), with collection-level `db.collection.bulkWrite()` mapping to insert/update/delete and working. Give a starting batch size as a starting point rather than a Learn figure (for example 1,000 operations per `insertMany`/`bulkWrite` call with `ordered: false` and a few parallel workers), never exceed the documented 25,000 writes per batch, and cite `migration-options` for the trial-and-extrapolate method; a per-tier figure is an open question. Advise building unique indexes in an idempotent deployment or migration script rather than at worker startup: Learn says a unique index build blocks writes on the collection (the engine's current default is non-blocking, so confirmation is pending; keep the conservative wording), and point to the DocumentDB-specific `createIndexes` option `blocking: true` for empty collections in migration utilities (`how-to-create-indexes`).
7. **Operator availability by server version.** Point to the compatibility table, give a detection one-liner (`db.version()` or `db.runCommand({ buildInfo: 1 })`), and show a worked server-side `$setWindowFields` running-max pipeline (`$setWindowFields` and its window operators are listed as supported on 5.0-8.0; note that `sortBy` is required for every bounded `documents` window and all `range` windows).

Companion fixes on existing pages that the new page links to:

- `how-to-transactions`: add the 30-second lifetime, cross-shard support, the code 263 command categories, the rule that `readConcern` cannot be set after the transaction starts, and the fact that 112/251 arrive without labels (with the application-level retry loop above).
- `troubleshoot-common-issues`: add rows for codes the engine emits that the table omits (6 `HostUnreachable`, 20 `IllegalOperation` on a replica cluster, 24 `LockTimeout`, 50 `ExceededTimeLimit`, 59 `CommandNotFound` for the 8.0 `bulkWrite` command, 91 `ShutdownInProgress`, 112 `WriteConflict`, 133 `FailedToSatisfyReadPreference`, 251 `NoSuchTransaction`, 261 `TooManyLogicalSessions`, 10107 `NotWritablePrimary`), list the commands that trigger 263, say that none of these carry MongoDB's transient-error labels, and add an explicit sentence that Azure DocumentDB has no request-unit throttling and never returns 16500 or 429.
- `compatibility-query-language`: footnote the `bulkWrite | No` row as the 8.0 database-level command; add rows or a note for error labels (`TransientTransactionError`, `UnknownTransactionCommitResult`, `RetryableWriteError`: not returned), retryable writes (not supported) and retryable reads; state that `getDefaultRWConcern` returns a constant the engine does not act on; reconcile the unique-index note ("block read and write operations") with `limitations` ("block writes").
- `limitations`: cross-link the 30-second transaction lifetime from `how-to-transactions`; in "Batch limits", name the error a client sees above 25,000 writes (on documentdb-local 0.117 a single command with 25,001 operations fails with code 16 `InvalidLength`, "Write batch size must fall within the range of 1 to 25000"; findings/phase4/ENGINE-TESTS.md) and state whether `hello.maxWriteBatchSize` reflects 25,000; add the retryable-writes statement from section 1.
- Write/read concern and read preference semantics (no page today): state them as in section 3, on this page or on `compatibility-query-language`.
- `cross-region-replication` vs `failover-modes`, `how-to-cluster-replica`, `troubleshoot-replication` and `reliability-documentdb`: the first says writes "continue seamlessly" through a promotion on the global read-write string while the others describe a short write gap, "a transient error" or "reconnect and retry"; the pages should agree and name the code a client sees (open question for engineering), so that the retry recipes in section 2 can cite them.

Related: the Agent Kit contradicts itself on `retryWrites` (its deployment skill says `retrywrites=false` is required, while three other skill files use `retryWrites: true`), its connection skill's retry helper retries only on codes 16500 and 429 (which the service never returns) and claims the driver retries transient errors automatically. Those fixes are tracked separately against Azure/documentdb-agent-kit using the same wording and facts as above; once this page exists the kit can link to it.

## Resolved

- retryWrites: answered 2026-11-25, see findings/phase4/DECISIONS.md. Retryable writes are not supported; retrywrites=false is required; the server does not de-duplicate retried writes (documentdb/documentdb#767).
- Write concern, read concern, read preference (2026-11-25, DECISIONS.md topic 9): the gateway validates and discards them; `w` 0/1/"majority" accepted and `w` of 2 or more rejected with `BadValue`; `j` and `wtimeout` accepted and ignored; `readConcern` `local`/`majority` accepted, `available`/`linearizable` rejected with `CommandNotSupported`; `readPreference` `primary`/`primaryPreferred`/`secondaryPreferred`/`nearest` discarded, `secondary` and tag sets rejected with `FailedToSatisfyReadPreference`, hedged reads with `BadValue`; `getDefaultRWConcern` returns a constant majority/majority "implicit" document; durability comes from HA.
