# Add modeling and query pattern recipes for applications

## What happens today

The Azure DocumentDB docs on Learn describe features and operators well, but no page tells an application developer how to model and index for a common app pattern, and the TOC has no data-modeling entry. The relevant guidance is scattered across operator, compatibility, indexing, change-stream and full-text-search pages, never phrased as "for a ledger / a status queue / a name-screening list, do this". Coding agents that search Learn land on an operator page, find no recipe, and fall back on generic MongoDB or Cosmos DB habits.

## Why it matters

In an experiment where an LLM coding agent (with the DocumentDB Agent Kit, the DocumentDB MCP server and the Learn MCP server) built 100 sample apps, 26 samples (48 findings) produced code that ran but broke a well-known DocumentDB practice. Counts are from one experiment run. The agent:

- stored money as JS `Number` or Python float (`parseFloat` on invoice totals) instead of Decimal128 or integer minor units;
- indexed only `{ lastUpdated: 1 }` for a `status + lastUpdated` query, with no compound or partial index and no `explain()`;
- ran unprefiltered, case-insensitive `$regex` over `name` and `alt_names` for fuzzy matching;
- grouped, bucketed and computed z-scores client-side instead of with `$group` / `$setWindowFields`;
- sent webhooks inline in change-stream handlers, with no delivery queue or dead-letter;
- added no collection validator despite strict Pydantic/Mongoose schemas, and was unsure `$bucket` and `$jsonSchema` were supported (the matrix lists both; collection-level validators are a gated preview, see item 2);
- improvised RAG patterns (client-side substring fallback, per-document vector upserts, no `/search` error contract) and lacked Mongoose/Beanie depth;
- asked for RU estimates, which do not exist on Azure DocumentDB (capacity is vCore tiers).

Samples are what customers copy first, so these become customer defaults.

## Proposed change

Add a TOC node **"Modeling and query patterns"** under `azure/documentdb`, next to Indexing, Change streams and Full-text search. Track it as one epic with one sub-issue per item; it is too large for a single PR. Each item is a short page or section; the page in brackets gets a "See also" link.

1. **Representing money** [`quickstart-nodejs-mongoose`, `quickstart-python-beanie`, `$toDecimal`]: store `Decimal128` or integer minor units plus currency, never double. Show Mongoose `Schema.Types.Decimal128`, pymongo `Decimal128("19.99")`, Beanie `Decimal`; in pipelines `{ $multiply: [ { $toDecimal: "$amount" }, { $toDecimal: "$rate" } ] }` and `$round` for presentation; one sentence on serializing Decimal128 to JSON in the API layer.
2. **Validate with `$jsonSchema`** [`compatibility-query-language`, `$jsonschema`, both ODM quickstarts]: `createCollection` with a `validator` and `validationLevel: "strict"`, an idempotent `collMod` upgrade path, and the matrix note on which operations are validated (insert, update, findAndModify, `$merge`/`$out`) and that `bypassDocumentValidation` skips it. State up front that collection-level validators are a gated preview (release notes 2025-10-10) whose enablement path is not yet documented on Learn, so `createCollection`/`collMod` with `validator`, `validationLevel` or `validationAction` returns `CommandNotSupported` "validator not supported yet" until the cluster has it; the recipe must degrade to application-side validation when that error is returned. Use only the documented keyword set: `properties`, `required`, `type`/`bsonType`, `pattern`, numeric and length bounds, `items`; `enum`, `additionalProperties`, `allOf`/`anyOf`/`oneOf`/`not`, `patternProperties` and `dependencies` are listed as unsupported on the `$jsonSchema` page, so express enumerations with `pattern` or an `$in` check in application code (`enum` and `oneOf` are in the engine's main branch but not documented for the service).
3. **Indexing filtered time-window and lookup queries, verified with explain** [extend `how-to-create-indexes`; link from `how-to-read-explain-output`, `index-advisor`]: equality-sort-range compound `{ status: 1, lastUpdated: 1 }` and the partial alternative with `partialFilterExpression`; precomputed keys (`day`, buckets) with an idempotent backfill; latest-rate lookup `{ from: 1, to: 1, effectiveDate: -1 }` queried with `sort({ effectiveDate: -1 }).limit(1)`, plus the `$lookup` + `$first` variant; a persisted normalized key (set in a pre-save hook, indexed, queried by equality) instead of `$regex`; a short `verify-indexes` script printing `winningPlan.stage` (COLLSCAN vs IXSCAN; for an aggregate explain the plan sits at `stages[0].$cursor.queryPlanner.winningPlan`), `totalDocsExamined`, `totalKeysExamined`, `executionTimeMillis` and `$indexStats`, with the sentence "Azure DocumentDB does not report request units; use docs/keys examined and execution time"; a pointer to Index Advisor for workload-level suggestions; and the statement that the service accepts and ignores `allowDiskUse` (it is on the engine's ignored-options list), so query memory is bounded by the tier (about 150 MiB on M80) and heavy pipelines must narrow their input with an indexed `$match` and `$limit` instead.
4. **Server-side aggregation** [`aggregate`, compatibility matrix]: timeline via indexed `$match` → `$sort` → `$group`, range pagination instead of `skip`; outliers via `$setWindowFields` with `$avg`/`$stdDevSamp` partitioned by day (every bounded `documents` window and every `range` window needs a `sortBy`; the engine errors "Missing sortBy field for document-based window" otherwise), plus the two-pass `$group` + `$lookup` variant; one line confirming `$bucket`, `$bucketAuto`, `$setWindowFields`, `$facet`, `$merge` support.
5. **Resilient change-stream consumer** [section on `change-streams`; link to its existing resume-token content rather than duplicate it]: the handler writes a `deliveries` record keyed by `change._id` and returns; a worker claims with `findOneAndUpdate`, retries with backoff and dead-letters after N attempts; incremental aggregates (update a per-cohort counter document from each event instead of recomputing nightly); prerequisites: single-shard clusters need no enablement step, while multishard change streams are preview, enabled in the portal (Settings > Features > "Change streams for multishard clusters") and cannot be enabled while the multishard rebalancer is on, and `updateDescription` is preview and opt-in per collection (`collMod` with `enableUpdateDescription`); restate the page's limitations: a single-shard to multi-shard topology transition breaks resumability, and cursors are reopened after failover [needs SME confirmation]; persist both the resume token and the last processed operation time, because resuming inside the active 400 MB change log is cheap, beyond it the service transparently reads archived logs at higher cost, and any non-resumable error (code undocumented) should fall back to `startAtOperationTime` from the last processed event time; historical change streams with PITR reach back up to 35 days or the cluster initialization point, whichever is earlier (per-tier window: see Open questions).
6. **Ledger design**: append-only collection, immutable audit fields, unique `idempotencyKey` (`createdAt`, `createdBy`, `transactionRef`, `source`; Mongoose `immutable: true`); never a TTL index on a ledger; expire derived data in a separate collection.
7. **Fuzzy name matching without `$regex`** [`full-text-search-fuzzy`, `full-text-search-custom-analyzers`]: prerequisite that full-text search is in preview and must be enabled on the cluster, self-serve (portal Settings > Features > Full-text search > Enable, or Azure CLI PATCH of `properties.previewFeatures` adding `FullTextSearch`, or Bicep/Terraform AzAPI), then wait 10 minutes before creating a search index; on a cluster without the preview, `createSearchIndexes` returns `CommandNotSupported` (code 115, "Search index creation is not supported yet"), which the recipe should treat as "feature not enabled yet"; poll `$listSearchIndexes` until `status: "READY"` and `queryable: true`; `createSearchIndexes` (`dynamic: false`) with `lowerCase` + `asciiFolding` + `edgeGram` on the index side and a `keyword` + `lowerCase` `searchAnalyzer`, queried with `$search` `text`; note that `autocomplete`, `regex` and `wildcard` operators inside `$search` are not supported, so use `edgeGram` for prefix matching; materialize `normalized_name` for exact hits; prefilter by country or shard key. Callout: "Do not run `{ $regex: ..., $options: 'i' }` over a whole collection in production. A case-insensitive, unanchored pattern cannot use an index selectively."
8. **ODM notes** [both ODM quickstarts]: Mongoose `strict: true` default and `strict: "throw"`, `immutable: true`, enum fields, a pre-save hook for normalized keys, `.lean()` + projection, a tenant-safety plugin that rejects `find`/`update`/`delete` without `tenantId`; Beanie 2.x on PyMongo's `AsyncMongoClient` only (Beanie 2 requires PyMongo >= 4.11; Learn's quickstart is tested with Beanie 2.2.0 and PyMongo 4.19.0), with the quickstart's own sentence that a Beanie 1 + Motor app must be updated first (Motor was deprecated 2025-05-14, end of life 2026-05-14; in the experiment Beanie 1 + Motor stacks failed with `MotorDatabase object is not callable` and `cannot import name '_QUERY_OPTIONS'`); Beanie `set()`/`update()` do not re-validate the full model, so validate a DTO first [needs SME confirmation], and aggregation should use the Beanie-initialized collection (`get_pymongo_collection()` in 2.x) [needs SME confirmation].
9. **RAG and agent patterns** [`vector-search`, `quickstart-python-vector-search`, `full-text-search-hybrid`]: vectors as `number[]` with `cosmosSearch` indexes (`vector-ivf`, `vector-hnsw`, `vector-diskann`), dimension limits 2,000 uncompressed, 4,000 with `compression: "half"` on HNSW or IVF, 16,000 with product quantization on DiskANN; state that BSON binary vectors (subtype 9) are stored and returned but not indexed, are silently absent from `cosmosSearch` results, and that a binary query vector is rejected ("expected an array type field"), so the page should name BSON binary explicitly rather than only "array of numbers"; batched `insert_many(..., ordered=False)` in batches of about 500–1000 (a starting point, not a Learn figure; the documented hard cap is 25,000 writes per batch request); detect index presence (`listIndexes` for the `cosmosSearch` index, `$listSearchIndexes` for text search indexes; both are supported, and the compatibility table row marking `$listSearchIndexes` unsupported is stale; read the vector index's options under either `cosmosSearch`, as Learn's "Get vector index definitions" sample shows, or `cosmosSearchOptions`, as the open-source engine returns, because the managed service's key is not yet verified) and fall back to a server-side `$search` or hybrid query, not client-side substring scoring; `fetch_k` of 5–10× `k` for client-side rerank, otherwise the server `cosmosSearch` `k`; agent memory as `raw_turns` (TTL on `occurredAt`, which must be a Date-typed single field; expiry lags by up to about a minute) plus `summaries` with `embedding: number[]` and `embedding_dim`; a minimal `/search` contract (400 on empty query, 502 on embedding failure, `similarity_score` in results); a short pymongo retry wrapper for transient errors; never pass connection strings or keys to the LLM, expose parameterized tools instead.
10. **Sharding in samples** [`partitioning`]: demos under about 100k documents stay single-shard; if a sample shards, show the shard key (`tenantId`, hashed `userId`) in code and in the `Microsoft.DocumentDB/mongoClusters` Bicep/ARM definition.

Do not write up as gaps: durable resume tokens (already on `change-streams`) and `$bucket` version checks (supported on 5.0–8.0).

Learn fixes the items above depend on (each is one line on an existing page):

- `compatibility-query-language`: the `$listSearchIndexes` row marks it unsupported while `full-text-search-keyword`, `full-text-search-structured` and `limitations` ("Search-index management supports creation and listing") use it; mark it supported. `compatibility-features` lists it as "Not prioritized" for the same reason.
- `full-text-search-overview`: document `CommandNotSupported` code 115 ("Search index creation is not supported yet") next to the enablement steps as the error seen before the preview is enabled.
- `aggregate` command reference: state that `allowDiskUse` is accepted and ignored; memory limits are per tier (`limitations`, about 150 MiB on M80).
- `how-to-read-explain-output`: show that an aggregate explain's plan sits at `stages[0].$cursor.queryPlanner.winningPlan`, and name the DocumentDB-specific fields (`explainVersion` 2, `runtimeFilterSet`, `indexFilterSet`, `isBitmap`, `estimatedTotalKeysExamined`).
- `$jsonschema` reference: say that collection validators are a gated preview returning "validator not supported yet" until enabled, link the release note, and reconcile the unsupported-keyword list with the engine (`enum`, `oneOf`).
- `indexing`: add a TTL section (`expireAfterSeconds`, single-field only, Date-typed values only, non-Date and missing values never expire, expiry lags by up to about a minute) and define when a partial index "qualifies" for `unique` (the engine accepts `$gt` and `$exists: true` filters).
- `change-streams`: document the error returned for a token that can no longer be resumed, and state the historical window per tier.

Related kit follow-up (not part of this Learn item): Azure/documentdb-agent-kit has no rule for Decimal128, `$jsonSchema` or a delivery-queue consumer, and no change-streams skill at all (filed separately as a new skill); it already has partial-index examples in `skills/indexing/index-pattern-cookbook.md`, and `skills/data-modeling/` covers embed-vs-reference, the 16 MB limit, denormalization, large-field split and schema versioning. Once these pages exist, the kit's `data-modeling` and `indexing` skills can link to them.

## Resolved

- Vector-index facts: settled 2026-11-25 from the Learn vector-search, half-precision, product-quantization and limitations pages, engine issue documentdb/documentdb#109, the product owner's answer and the engine tests, see findings/phase4/DECISIONS.md.
  - Dimension limits quoted in item 9: 2,000 uncompressed; 4,000 with `compression: "half"` on HNSW or IVF; 16,000 with product quantization on DiskANN (vector-search "Features and limitations", half-precision, product-quantization and limitations pages). The product owner confirmed these limits on 2026-11-25 and said the select-algorithm quickstarts' HNSW 8,000 figure is wrong (the fix belongs in `ai/includes/choosing-algorithm.md` of Azure-Samples/documentdb-samples), so it is not quoted here (DECISIONS.md, vector indexes).
  - BSON binary vectors are stored and returned intact but are not indexed by any `cosmosSearch` index kind, are silently absent from results, and a binary query vector is rejected; Learn requires an array of numbers (vector-search page, DiskANN field table and IVF Important box; engine issue documentdb/documentdb#109, closed completed 2026-04-28).
  - `listIndexes` shape (corrected 2026-11-25): Learn's vector-search sample ("Get vector index definitions") shows the vector-index options under `cosmosSearch`, but the open-source engine 0.117 (documentdb-local) returns them under `cosmosSearchOptions` with no `cosmosSearch` key (findings/phase4/ENGINE-TESTS.md; engine-tests/vector-index-rules). The managed service is not yet checked, so item 9's index-presence check reads both keys (DECISIONS.md, vector indexes, `listIndexes`).
- `$listSearchIndexes` support (former open question 1): supported; the keyword, structured and limitations pages and the 2026-11-17 DocumentDB blog post all use it to wait for `status: "READY"` and `queryable: true`, and the `compatibility-query-language` row (dated 2025-11-05) marking it unsupported is stale (settled 2026-11-25, DECISIONS.md topic 7; rests on documentation, no run called it).
- Preview status (former open question 2): full-text search is still preview, self-serve enablement with a 10-minute wait (`full-text-search-overview`, updated 2026-11-17; DocumentDB blog 2026-11-17); multishard change streams and `updateDescription` are still preview, single-shard change streams need no enablement step (`change-streams`, updated 2026-11-17; observed in run 07-lab-results-aggregator). Items 5 and 7 keep the prerequisite wording (DECISIONS.md topics 7 and 8).
- Change-stream limits (former open question 3, in part): historical recovery "can extend up to 35 days or the cluster initialization point, whichever is earlier"; the active change log is 400 MB and older entries are read transparently from archived logs; "Cluster topology transition from single-shard to multi-shard breaks change stream resumability" (`change-streams`, Important box and Limitations; DECISIONS.md topic 8). The per-tier window and the failover restatement stay open below.
- Beanie version (former open question 4, in part): the recipe targets Beanie 2.x on PyMongo `AsyncMongoClient` (PyMongo >= 4.11; Learn tested Beanie 2.2.0 and PyMongo 4.19.0) and drops the Beanie 1.x/Motor accessor, since the Beanie quickstart tells Beanie 1 + Motor apps to update first and Motor is deprecated (quickstart-python-beanie, updated 2026-11-24; Motor docs; DECISIONS.md topic 4, item 4.6). The `set()`/`update()` validation and accessor-name claims stay open below.
- `allowDiskUse` (item 3): accepted and ignored by the engine (`commands_common.c` IgnoredCommonSpecFields; observed accepted in run 02-ai-powered-product-recommendations); query memory is per tier (`limitations`; DECISIONS.md topic 10).
- Collection validators (item 2): gated preview (release notes 2025-10-10), engine returns `CommandNotSupported` "validator not supported yet" until enabled, enablement not documented on Learn; `$jsonSchema` page lists `enum`, `additionalProperties`, `allOf`/`anyOf`/`oneOf`/`not`, `patternProperties`, `dependencies` as unsupported (DECISIONS.md topic 10).
