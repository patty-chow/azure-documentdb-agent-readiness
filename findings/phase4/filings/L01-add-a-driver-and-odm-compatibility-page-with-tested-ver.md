# Add a driver and ODM compatibility page with tested versions and client options, linked from every quickstart

## What happens today

Azure DocumentDB's Learn docs already know the tested driver pairings, but only as a "Tested driver version" sub-heading on individual ODM quickstarts:

- `quickstart-nodejs-mongoose`: MongoDB Node.js driver 7.8.0 via Mongoose 9.12.1, Node 22.12+.
- `quickstart-python-beanie`: Beanie 2.2.0 with PyMongo 4.19.0 (`AsyncMongoClient`, not Motor), Python 3.13.
- `quickstart-python-django`: Django MongoDB Backend 6.1.0 with PyMongo 4.19.0 (Django 6.1.3), Python 3.13.
- ODM quickstarts also exist for Prisma, Spring Data MongoDB and EF Core; whether each has a tested-version block was not checked.

Nothing ties these together or covers other stacks:

- `quickstart-python` (`pip install pymongo`) and `quickstart-nodejs` (`npm install mongodb`) are unpinned and state no tested version. `quickstart-python` says "Python 3.12 or later" while the Beanie and Django pages say 3.13 (PyMongo 4.19 itself requires Python 3.11 or later), and it never says when to use `AsyncMongoClient` instead of Motor. `quickstart-nodejs` requires "Node.js 22 or newer"; MongoDB marks only driver 7.x as compatible with Node 24, so a reader on Node 24 with a 6.x lockfile is in an untested combination.
- The other driver quickstarts publish no tested versions either: `quickstart-java` pins `mongodb-driver-sync` 5.2.0 while `how-to-build-java-console-app` (newer, updated 2026-11-23) pins 5.4.0, neither marked as tested; `quickstart-dotnet` (`dotnet add package MongoDB.Driver`), `quickstart-go` (`go get go.mongodb.org/mongo-driver/v2/mongo`) and `quickstart-rust` (`cargo add mongodb`) install unpinned. Microsoft's own Azure-Samples/documentdb-samples repository pins differently again (MongoDB.Driver 3.0.0 and 3.2.0, `pymongo>=4.6.0` and `>=4.7.0`, `mongodb ^6.18.0` and `^7.1.0`, as lower bounds rather than tested versions) and its three Go samples use the v1 module (`go.mongodb.org/mongo-driver v1.17.6`), whose import paths differ from the v2 module the Go quickstart teaches.
- `query-knowledge-base` (LlamaIndex) installs its packages unpinned although its prose is specific to `llama-index-vector-stores-azurecosmosmongo` 0.9.0, the current release (requires `llama-index-core>=0.13.0,<0.15` and `pymongo>=4.6.1,<5`); it has no Python prerequisite.
- `how-to-connect-role-based-access-control` shows `MONGODB-OIDC` code but no minimum driver version. The floors are in the driver release notes, not on Learn: PyMongo 4.7, Node `mongodb` 6.7.0, Java driver 5.1, .NET driver 2.25.0. The page has Python, TypeScript and C# samples only; the Java callback exists only on `how-to-build-java-console-app`.
- The FAQ lists supported wire protocol versions (5.0 to 8.0) and says any driver that supports the wire protocol connects, but gives no per-language driver table or minimum version. The *Compatibility* TOC node has no drivers page; `/compatibility` and `/driver-compatibility` return 404.
- No page maps `writeConcern`, `readConcern` and `readPreference` to service behaviour, gives pool and timeout recommendations, or says that `useNewUrlParser` / `useUnifiedTopology` do nothing in current drivers. The DocumentDB gateway source shows that the service validates these options and does not act on them (`w: 0`, `1` and `"majority"` accepted, `w` of 2 or more rejected; `readConcern` `local` and `majority` accepted, `available` and `linearizable` rejected; `readPreference` `secondary`, tag sets and hedged reads rejected, the other modes accepted and discarded; every read is served by the primary shards) and that durability is set by the cluster's HA configuration, but no Learn page says so. The `high-availability` page says primary and standby shards use synchronous replication with zero data loss on failover, but does not tie that to concern values. The Mongoose tutorial uses `maxPoolSize: 10` and `serverSelectionTimeoutMS: 30000` without explaining them; other quickstarts show a bare client. `compute-storage` publishes no connection limit per tier.
- Pages are inconsistent on retryable writes. The portal connection string and every quickstart include `retrywrites=false`, which is required because Azure DocumentDB does not support retryable writes, but the Mongoose tutorial calls the value "a sample" rather than a requirement, and no Learn page (limitations, compatibility, connect) explains why the setting is required.

## Why it matters

In one experiment run, a coding agent (gpt-5-mini with the DocumentDB Agent Kit and Learn MCP) built 100 sample apps. 114 findings across **64 of the 100 samples** trace to this gap. Counts are from that single run and are approximate. With no general page to find, the agent picked versions from model memory, which are about two years stale:

- 21 of 22 Mongoose samples pinned `^7.x`; 16 of 26 direct-driver Node samples pinned `mongodb ^5.x`. Agents invented versions that do not exist (`mongodb@^5.10.0`, `mongoose@7.14.0`) and hit `npm notarget` in 13 runs.
- 17 Python samples used Motor and only 1 used `AsyncMongoClient`; most Beanie samples pinned Beanie 1.x, the stack the Beanie quickstart tells readers to leave. Results included `init_beanie` failures ("MotorDatabase object is not callable"), `cannot import name _QUERY_OPTIONS from pymongo.cursor`, and pydantic-core source builds on Python 3.13 (old pydantic 2.x pins such as `pydantic==2.6.1` ship no cp313 wheel) [needs SME confirmation: the reviewer flags Python 3.13 install failures as possibly a harness artifact]. Several agents dropped Beanie or LangChain to get a green build.
- 10 audits could not verify driver pins, concern levels or pool settings against any public source, so a points ledger shipped with `w: "majority"` assumptions copied from generic MongoDB guidance.

Agent logs show no ODM quickstart was opened during builds: the per-page note is correct but not discoverable.

The reviewer notes that sample counts in this experiment are unstable and should be re-checked after the harness fixes before they are quoted externally [needs SME confirmation].

- **Mongoose production configuration**: `autoIndex: false`, `autoCreate: false`, `bufferCommands: false`, then `Model.createCollection()` / `Model.createIndexes()` in a seed or migration script, with a sentence on why (the Mongoose quickstart already does this).
- **Consistency table**: state up front that Azure DocumentDB validates `writeConcern`, `readConcern` and `readPreference` and does not act on them; durability is a cluster property set by in-region HA (writes are acknowledged after commit on both the primary and the standby shard), not by `w`. Rows, from the DocumentDB gateway source: `w: 0`, `w: 1` and `w: "majority"` accepted and ignored; `w` of 2 to 50 rejected with BadValue ("w value exceeds the number of data-bearing voting members"); `j` and `wtimeout` accepted and ignored; `readConcern` `local` and `majority` accepted, `available` and `linearizable` rejected with CommandNotSupported, `snapshot` rejected unless enabled on the gateway (open question 3); `readPreference` `primary`, `primaryPreferred`, `secondaryPreferred` and `nearest` accepted and dropped (every read is served by the primary shards; standby shards never serve reads, with or without HA), `secondary` and any tag set rejected with FailedToSatisfyReadPreference, hedged reads rejected with BadValue; reads from a replica cluster use that cluster's own connection string. Note that `getDefaultRWConcern` returns a constant `{ defaultReadConcern: { level: "majority" }, defaultWriteConcern: { w: "majority", wtimeout: 0 } }` that does not describe applied behaviour. Recommend leaving all three options at their defaults and never configuring `readPreference: secondary` or tag sets, which fail rather than fall back to the primary. Link the synchronous-replication statement on the `high-availability` page. This is also the Learn fix recorded in DECISIONS.md: no Learn page documents these semantics today.
- **Pool and timeout table**: `maxPoolSize`, `minPoolSize`, `serverSelectionTimeoutMS`, `socketTimeoutMS`, `maxIdleTimeMS` for Functions, App Service/containers and batch jobs [needs SME confirmation], explaining the `maxPoolSize: 10` / `serverSelectionTimeoutMS: 30000` values the Mongoose tutorial uses. State what is known: `compute-storage` publishes no connection limit per tier; the service has no request-unit throttling and never returns 16500 or 429; the only admission error in the engine is 261 TooManyLogicalSessions ("There are too many open connections."), which is not retried, so size pools conservatively and treat 261 as "reduce connections", not "back off and retry"; the default query execution limit is 120 seconds (`maxTimeMS` overrides it per query) and the transaction lifetime is 30 seconds.
- **Pinning**: pin direct dependencies to the tested versions, commit `package-lock.json` / `constraints.txt`, install with `npm ci` / `pip install -c constraints.txt`, and re-pin by re-running the quickstart rather than widening ranges.
