## Notes

I first inspected the sample app to see which areas matter (connection handling, singleton client, cursor-based batching, partial and unique indexes, unordered bulk writes, UTC timestamps and immutability, monitoring, and vector-index-capable cluster). I searched Microsoft Learn and loaded several installed skills that contain focused guidance for Azure DocumentDB (connection, driver, indexing, query optimization, vector search, security, monitoring, data modeling, local deployment). Public Microsoft docs confirm most of the prior beliefs (connection via env/Key Vault, TLS required, Private Link, singleton client pattern, pool tuning, cursor/batchSize, avoid skip, partial/unique/TTL indexes, index creation guidance, monitoring RUs and 429 handling, using Retry-After and backoff, transaction limitations, document size limits, and CMK/Key Vault practices). A few prior beliefs are not present as explicit numeric rules in the public docs (for example a precise recommended unordered bulkWrite batch size like '200–1000 ops'); these are left as prior_knowledge_only in the searches_with_no_useful_result list so the product team can see where the public record is silent.

Prior beliefs the discovery step did not classify: K01, K02, K17. See 05a-prior-beliefs.json.
