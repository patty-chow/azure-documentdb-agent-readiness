# 1. Prompt review: 14-customer-complaint-classifier

**Verdict: sufficient_with_assumptions**

The starter prompt plus the provided skill_md give a clear, actionable goal: a Python LangChain + Beanie pipeline that classifies, embeds, stores, and aggregates complaint documents against an existing vector-capable Azure DocumentDB cluster. The build can start, but many implementation details (models, exact schema, API surface, index dimensions/params, tests, seed-data source, and README/infra artifacts) are left to the implementer or other skills to decide.

## Reference requirements at risk

- Create the cosmosSearch vector index in code on the embedding field with dimensions matching the embedding model used — not explicitly specified in prompt; index creation and exact dimensions are left to implementer.
- Vector index parameters tuned for sample size and README explaining how to change them for larger datasets — prompt/skill guidance on parameters exists but no explicit parameters or README instruction requirement.
- Sample data source, size, license and an idempotent seed script that can be run twice without duplicating data — no data source is specified in the prompt.
- /search should return a clear error for an empty query and when the embedding call fails — error behavior not specified in prompt.
- Search results should include a similarity score — prompt requests similarity search but does not require returning scores.
- Dependencies pinned in requirements.txt — prompt asks for Python, but not explicit dependency pinning.
- Unit tests that run without a live cluster (mocks) — prompt doesn't mention tests or mocking strategy.
- Infrastructure-as-code for the cluster using the Azure DocumentDB resource type — prompt and skill_md imply using existing cluster, so infra code is not requested.
- README covering what the sample shows, prerequisites, setup, run, and clean-up — prompt doesn't ask explicitly for a README, though skill_md expects verification steps.

## Questions for the prompt author

- Which embedding model and provider should be used (model name and dims)? This determines the vector index dimension and cost assumptions.
- Which LLM model / provider should the LangChain agent use for classification (name or constraints on cost / latency)?
- Preferred app surface: FastAPI endpoints (recommended) or CLI-only scripts? If API, confirm required routes (classify, search, hotspots) and expected inputs.
- Should the sample include infra-as-code (Bicep/Terraform) to create the DocumentDB cluster, or explicitly avoid provisioning and use the provided cluster? (skill_md suggests using existing cluster).
- Do you want a seeded dataset provided in the repo (and if so, any real data / license constraints) or synthetic sample data generated by script?
