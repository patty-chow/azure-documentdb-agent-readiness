- **The source says:** PRIOR_K01: The public Azure DocumentDB guidance recommends using PyMongo's AsyncMongoClient (one process-wide client) rather than Motor; creating a Motor-specific singleton is not the recommended Python async pattern.
- **Source:** [documentdb-connection](https://github.com/Azure/documentdb-agent-kit/blob/main/skills/connection/SKILL.md)

### P34: PRIOR_K04: Azure DocumentDB maps/controls consistency itself and ignores client-specified writeConcern (writes are quorum/mapped to account consistency); do not rely on setting writeConcern on the client to achieve provider-level durability semantics.

- **The model believed:** Set explicit readConcern/readPreference and writeConcern appropriate to your durability/latency needs (e.g. w=majority for stronger durability or w=1 for lower latency) and test behavior under expected failure modes. (knowledge of `mongodb`)
- **The source says:** PRIOR_K04: Azure DocumentDB maps/controls consistency itself and ignores client-specified writeConcern (writes are quorum/mapped to account consistency); do not rely on setting writeConcern on the client to achieve provider-level durability semantics.
- **Source:** [MongoDB Query Language (MQL) compatibility in Azure DocumentDB / feature support](https://learn.microsoft.com/azure/documentdb/compatibility-query-language#database-commands)

### P35: PRIOR_K05: Implement idempotent retries with exponential backoff for transient errors; do not rely on driver retryable writes on Azure DocumentDB (set retryWrites=false for many deployments) and use retryable reads where supported.
