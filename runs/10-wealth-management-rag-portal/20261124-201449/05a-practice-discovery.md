## Where public sources contradict the model

### P03: Set retryWrites=false in the connection string for Azure DocumentDB and do not rely on the driver's automatic retryWrites behavior for non-idempotent operations.

- **The model believed:** Enable server-side retryWrites and configure the driver to use sensible serverSelectionTimeoutMS and socketTimeoutMS to avoid long request hangs; handle DuplicateKey and idempotency explicitly for write retries. (knowledge of `mongodb`)
- **The source says:** Set retryWrites=false in the connection string for Azure DocumentDB and do not rely on the driver's automatic retryWrites behavior for non-idempotent operations.
- **Source:** [Migrate from Amazon DocumentDB to Azure DocumentDB (with MongoDB compatibility)](https://learn.microsoft.com/azure/documentdb/migrate-amazon-documentdb#update-your-application)

### P13: Don't assume client-specified MongoDB writeConcern will control durability; Azure DocumentDB maps/makes writes quorum/majority at the service level and client writeConcern may be ignored—use account-level consistency settings to reason about read-after-write behavior.

- **The model believed:** Use writeConcern 'majority' (or the equivalent durable write setting) for portfolio upserts when the application requires read-after-write consistency, or explicitly read with majority readConcern after a critical write. (knowledge of `mongodb`)
- **The source says:** Don't assume client-specified MongoDB writeConcern will control durability; Azure DocumentDB maps/makes writes quorum/majority at the service level and client writeConcern may be ignored—use account-level consistency settings to reason about read-after-write behavior.
- **Source:** [Consistency levels for Azure Cosmos DB and the API for MongoDB](https://learn.microsoft.com/azure/cosmos-db/mongodb/consistency-mapping)

## Notes

I inspected the workspace and app code (it uses DOCUMENTDB_URI env var, a module-level singleton MongoClient, creates cosmosSearch vector indexes via createIndexes/cosmosSearchOptions, normalizes embeddings for cosine similarity, stores embeddings in a research_documents collection and portfolios separately, and falls back to client-side scoring when no native index is present). Public Microsoft documentation (Integrated vector store, quickstarts, security, and reliability pages) supports the majority of the agent's prior beliefs (connection-string secrecy, single MongoClient reuse, TLS/private endpoints, Entra ID, embedding model metadata, vector-index tuning/algorithms, hybrid filter indexes, projection usage, transient-fault retry patterns, testing with dedicated databases, monitoring). The main prior-belief mismatches are: drivers' retryWrites should be set to false for Azure DocumentDB (contradicting an assumption to enable driver-managed retryWrites), and client writeConcern 'majority' is not a reliable way to request durability because the service maps consistency at the account level and may ignore client writeConcern settings. One prior belief (K05: mandate to keep embeddings in a separate dedicated collection) had no Azure-documentation saying you must do that; Azure docs generally recommend the integrated vector store (storing embeddings alongside original data) but do not forbid separate collections — therefore K05 is treated as prior_knowledge_only. For each prior belief I marked whether the public docs confirmed or contradicted it and supplied the exact page used as evidence.

Prior beliefs the discovery step did not classify: K07, K15, K18, K19. See 05a-prior-beliefs.json.
