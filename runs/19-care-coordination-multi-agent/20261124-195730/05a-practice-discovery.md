## Where public sources contradict the model

### P16: Do not rely on client-specified writeConcern/readConcern for durability in Azure DocumentDB because the service maps/ignores client writeConcern; use the service consistency model and understand how it maps to MongoDB driver options.

- **The model believed:** Set an appropriate writeConcern/readConcern (or equivalent) for operations that must be durable/consistent (for example, w=majority for writes that must be persisted before continuing) and use lower w when lower latency is acceptable. (knowledge of `mongodb`)
- **The source says:** Do not rely on client-specified writeConcern/readConcern for durability in Azure DocumentDB because the service maps/ignores client writeConcern; use the service consistency model and understand how it maps to MongoDB driver options.
- **Source:** [Supported features and syntax in Azure Cosmos DB for MongoDB (write concern mapping)](https://learn.microsoft.com/azure/cosmos-db/mongodb/feature-support-70#time-to-live)

## Notes

I scanned Azure DocumentDB documentation (quickstarts, vector-search, indexing, security, sharding, autoscale, monitoring) and related Microsoft guidance. Most of the sample app's best-practice priors are supported by Azure DocumentDB docs (connection string via env, singleton MongoClient, index/explain usage, vector-index configuration, sharding guidance, autoscale, upsert idempotent seeding, monitoring). The notable contradiction is client writeConcern/readConcern: Azure maps or ignores client writeConcern and you should design around the service consistency model rather than expecting driver-level w=majority to be honored. Three prior beliefs had no clear Azure DocumentDB page that explicitly states them (keep PHI out of logs in product docs, explicit schema_version mandate, and provenance metadata for LLM outputs) so they are recorded as prior_knowledge_only with the searches attempted.
