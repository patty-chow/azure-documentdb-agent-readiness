# 1. Prompt review: 09-lead-scoring-agent

**Verdict: sufficient_with_assumptions**

The starter prompt clearly defines the goal (a single Node.js LangChain agent that fetches documents from Azure DocumentDB, reasons, assigns a 0–100 score, and writes the score + one-paragraph rationale back). Many operational details (driver version, exact collection names and schemas, embedding/chat models, API surface, seed data, README and infra-as-code) are left unspecified and will be filled by the builder using defaults or guidance from the installed DocumentDB skills.

## Reference requirements at risk

- The connection string and model credentials come from environment variables; none appear in the repository. Reason: skill_md specifies DOCUMENTDB_URI but the prompt doesn't mention model creds or explicit env var names for LLM/embedding API keys.
- A `.env.example` lists every setting with placeholder values. Reason: prompt asks to use DocumentDB skill but doesn't explicitly require .env.example; builder may add it, but not guaranteed.
- The vector index dimensions match the embedding model's output. Reason: no embedding model/dimensions specified in the prompt; this needs explicit choice.
- The vector index parameters are chosen for the sample's data size, and the README says how to change them for a larger one. Reason: prompt doesn't ask for index parameters or scaling guidance; skill provides best-practice but not specific numbers for this sample.
- A seed script loads sample data and creates the index, and can be run twice without duplicating data. Reason: prompt asks for an agent but not explicit seed script requirements; builder may create one, but it's not specified.
- Dependencies are pinned in `requirements.txt` (or equivalent lockfile). Reason: prompt doesn't mention dependency pinning; Node.js samples should include package-lock.json but prompt doesn't require it.
- Unit tests run without a live cluster. Reason: prompt doesn't require mocking or test strategy; installed skills mention testing best-practices but not explicit test implementations.
- Infrastructure for the cluster is provided as code, using the Azure DocumentDB resource type. Reason: prompt does not request provisioning; run environment forbids creating a new cluster, so an infra-as-code artifact may be omitted.
- The README covers what the sample shows, prerequisites, setup, run, and clean-up. Reason: prompt asks to build sample but does not explicitly require a README (though the skill_md suggests verifying and recording actions).
- The sample uses the name "Azure DocumentDB" throughout, and no former or neighbouring product name. Reason: prompt doesn't constrain naming; builder must be careful to use the requested product name.

## Questions for the prompt author

- Which embedding model and chat model / provider should the sample use (e.g., OpenAI text-embedding-3-small + gpt-4o-mini)? the choice determines vector dimension and index settings.
- Which API surface do you prefer for the sample: an HTTP endpoint (POST /score-lead) or a CLI script? This changes how the agent is invoked and tested.
- Do you want concrete collection names and document schemas (e.g., leads, activities, companies, engagement_signals) or should the builder pick sensible defaults and document them?
- Should the repository include infra-as-code (Bicep/Terraform) for the cluster, or must the sample avoid any cloud provisioning (per skill_md instruction to not create additional clusters)?
