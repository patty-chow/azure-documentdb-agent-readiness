## Where public sources contradict the model

### P06: Do not assume MongoDB driver's retryable-writes should be enabled by default for Azure DocumentDB; many Azure samples set retryWrites=false and some features (vector index workflows) require retryWrites=false.

- **The model believed:** Enable retryable writes (retryWrites=true) and idempotent write patterns in the client when supported by the server to reduce error handling complexity for transient failures. (knowledge of `mongodb`)
- **The source says:** Do not assume MongoDB driver's retryable-writes should be enabled by default for Azure DocumentDB; many Azure samples set retryWrites=false and some features (vector index workflows) require retryWrites=false.
- **Source:** [Use Mongoose with Azure DocumentDB: Build a Node.js inventory API](https://learn.microsoft.com/azure/documentdb/tutorial-nodejs-mongoose#create-the-project)

### P14: Multi-document transactions are limited: use transactions only within a single (nonsharded) collection; cross-collection multi-document transactions are not supported.

- **The model believed:** Use multi-document transactions when creating the household document and updating customer documents in a single logical operation to maintain consistency (commit both the household doc and member updates in one transaction). (knowledge of `mongodb`)
- **The source says:** Multi-document transactions are limited: use transactions only within a single (nonsharded) collection; cross-collection multi-document transactions are not supported.
- **Source:** [Supported features and syntax in Azure Cosmos DB for MongoDB 6.0 server version](https://learn.microsoft.com/azure/cosmos-db/mongodb/feature-support-60#transactions)

### P27: Client-specified writeConcern is ignored by the service: Azure DocumentDB maps writes to its own consistency model (quorum/Session); do not rely on client writeConcern settings like w:'majority' to change durability semantics on the service.

- **The model believed:** Use an appropriate write concern (acknowledged writes or w: 'majority' where durability matters) for household creation and membership changes; evaluate performance impact before using majority everywhere. (knowledge of `mongodb`)
- **The source says:** Client-specified writeConcern is ignored by the service: Azure DocumentDB maps writes to its own consistency model (quorum/Session); do not rely on client writeConcern settings like w:'majority' to change durability semantics on the service.
- **Source:** [Supported features and syntax in Azure Cosmos DB for MongoDB 6.0 server version](https://learn.microsoft.com/azure/cosmos-db/mongodb/feature-support-60#write-concern)
