# Reference requirements: Regulatory compliance RAG checker

> Drafted by the model from the sample's title, description, concepts and starter prompt, then
> reviewed by a person. The builder never sees this file. The prompt reviewer predicts which
> lines the starter prompt will miss, and the auditor checks each line against what was built.
>
> One requirement per bullet, each something a reviewer can check in the code.

## What the starter prompt asks for

- Build a Python RAG agent with LlamaIndex in which one agent handles the whole flow for a given policy excerpt: retrieving the relevant regulatory clauses, comparing them against the excerpt and producing the compliance gap report.
- Ingest regulatory documents into one Azure DocumentDB collection and internal policy documents into a second, separate collection (e.g. through pymongo or a LlamaIndex vector store integration), storing on each document its text and the embedding array produced by the embedding model configured in LlamaIndex.
- Create a cosmosSearch vector index (kind vector-ivf, vector-hnsw or vector-diskann) on the embedding field of each collection in code, with dimensions matching the embedding model's output.
- When given a policy excerpt, embed it and retrieve the most relevant regulatory clauses by running a $search / cosmosSearch vector similarity query (similarity COS, L2 or IP) against the regulatory collection in Azure DocumentDB, returning the top-k clauses (e.g. k = 5).
- Apply context engineering to build the comparison prompt: assemble a structured prompt that places the policy excerpt and the retrieved regulatory clauses in distinct, labelled sections and instructs the LLM to compare the policy excerpt against those clauses.
- Produce a compliance gap report as the agent's output, generated by the LLM through LlamaIndex from that structured comparison prompt, identifying where the policy excerpt meets and where it falls short of the retrieved regulatory clauses.

## What a gallery sample also needs (the starter prompt does not say these)

- The connection string and model credentials come from environment variables; none appear in the repository.
- A `.env.example` lists every setting with placeholder values.
- The vector index dimensions match the embedding model's output.
- The vector index parameters are chosen for the sample's data size, and the README says how to change them for a larger one.
- One database client is created and reused across requests.
- A seed script loads sample data and creates the index, and can be run twice without duplicating data.
- `/search` returns a clear error for an empty query and when the embedding call fails.
- Search results include the similarity score.
- Dependencies are pinned in `requirements.txt`.
- Unit tests run without a live cluster.
- Infrastructure for the cluster is provided as code, using the Azure DocumentDB resource type.
- The README covers what the sample shows, prerequisites, setup, run, and clean-up.
- The sample uses the name "Azure DocumentDB" throughout, and no former or neighbouring product name.
