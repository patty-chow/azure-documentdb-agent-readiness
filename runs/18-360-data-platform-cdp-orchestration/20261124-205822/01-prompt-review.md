# 1. Prompt review: 18-360-data-platform-cdp-orchestration

**Verdict: sufficient_with_assumptions**

The starter prompt clearly states the goal (Python + LangChain multi-agent orchestration) and the main behaviors (ingest → dedup (LLM-assisted) → enrich, and workflow logging). Many implementation details (driver version, DB client pattern, vector/index guidance, data-model patterns, local dev conventions) are covered by the installed DocumentDB skills, so a builder can start. Several operational and sample-convention details are left unspecified and will be filled by sensible defaults unless the author specifies them (LLM provider/model, exact data shapes, seed data, CI/test strategy, README/IaC).

## Reference requirements at risk

- Model credentials come from environment variables: prompt/skill_md mentions DOCUMENTDB_URI but does not specify where to store LLM/model keys; risk that model creds may not be put into env-only (no skill enforces that for LLM provider).
- .env.example lists every setting with placeholder values: prompt directs to use a .env.example but does not enumerate all settings; risk it will be incomplete.
- Vector index dimensions match the embedding model's output: prompt requests enrichment/dedup with LLMs but doesn't state embedding model/dimensions; risk the created vector index will not match the model unless the builder chooses a compatible model.
- Vector index parameters chosen for the sample's data size and README guidance on changing them: prompt doesn’t require tuning docs; risk that parameters will be defaults without explanation.
- A seed script loads sample data and creates the index, and can be run twice without duplicating data: prompt doesn't ask for this; risk the sample omits an idempotent seed script.
- /search returns a clear error for an empty query and when the embedding call fails: prompt doesn't mention a search surface or error handling for embeddings; risk these checks are missing.
- Search results include the similarity score: prompt doesn't require exposing similarity score in results; risk the sample omits it.
- Dependencies are pinned in requirements.txt: prompt doesn't require pinned deps; risk unpinned dependencies.
- Unit tests run without a live cluster: prompt doesn't require mocking or offline tests; risk tests require the live cluster and cannot run in CI.
- Infrastructure for the cluster is provided as code using the Azure DocumentDB resource type: prompt explicitly uses an existing cluster and doesn't require IaC; risk that no IaC will be included.
- README covers what the sample shows, prerequisites, setup, run, and clean-up: prompt doesn't require a README; risk documentation will be thin or missing.
- The sample uses the name 'Azure DocumentDB' throughout and no former/neighbouring product name: prompt uses 'DocumentDB' and skill_md clarifies 'Azure DocumentDB', but nothing enforces consistent naming in README and code; risk of inconsistent naming.

## Questions for the prompt author

- Which LLM provider and exact models should the sample use for (a) LLM-assisted duplicate matching and (b) embeddings? (This changes the embedding dimensionality and index shape.)
- Should the sample expose a public API (FastAPI) for running batches and searching, or is a CLI/script-only sample sufficient?
- Do you want an idempotent seed script and included sample data in the repo (recommended for galleries), or should the sample rely on external data the user supplies?
- Should the sample include optional IaC (Bicep/Terraform) to provision the DocumentDB cluster, or must it avoid any provisioning (use existing cluster only)?

## Contradictions and missing references

- Prompt says "Using the DocumentDB skill" but there is no installed skill with the exact name "DocumentDB"; instead many documentdb-* skills are available (e.g. documentdb-driver, documentdb-vector-search). The builder will interpret this as 'use the DocumentDB-related skills'.
